The sandbox lets you validate your whole integration before going live. It uses the same requests and responses as production.

| | Value |
| --- | --- |
| API base URL | `https://api.stg.hellopay.com.co` |
| Portal | [portal.stg.hellopay.com.co](https://portal.stg.hellopay.com.co) |
| API key | Create one in the sandbox portal. See [Authentication](/getting-started/authentication) |

No real money moves. The sandbox does not connect to PSE, Bre-B, or Nequi: it simulates their behavior, including the async `sourceData` updates and webhooks.

## Test document numbers

The value of `inlineCustomer.idNumber` decides the final status of a payin or payout:

| `inlineCustomer.idNumber` | Final status | Webhook |
| --- | --- | --- |
| `1000000001` | `CONFIRMED` | `payin.confirmed` / `payout.confirmed` |
| `1000000003` | `DECLINED` (`errorCode: SANDBOX_DECLINED`) | `payin.declined` / `payout.declined` |
| `1000000005` | `CANCELED` | `payin.canceled` / `payout.canceled` |
| Any other value | `CONFIRMED` | `payin.confirmed` / `payout.confirmed` |

<Tip>
  Use `1000000001` when you want a success, rather than a random number. Your tests then read clearly and keep working if the default changes.
</Tip>

1. The create response returns `status: "PENDING"`.
2. Within a few seconds, HelloPay prepares the rail data and moves the transaction to `PROCESSING`. Payins send `payin.processing`. Payouts do not send a webhook for this step.
3. About 5 seconds later, the transaction reaches the final status from the table above, and HelloPay sends the matching webhook.

## Rail behavior in the sandbox

| Rail | What the sandbox returns |
| --- | --- |
| `PSE` | `sourceData.pseUrl` is `null` at creation, then a sandbox redirect URL |
| `BRE_B` | `sourceData.keyString` such as `@SANDBOX5AF43BE4F5`. `QR_CODE` also returns a fixed test QR in `sourceData.qrString` |
| `NEQUI` | `sourceData.phone` equals `inlineCustomer.phone`. No real Nequi request is sent |
| Payouts (`BRE_B`) | `targetData.keyString` echoes the destination key. The key is not checked: the outcome depends only on `idNumber`, and `targetData.bank` is not added. Use `@alphamunKey01` to test `GET /breb/keys/{keyString}` |

## Suggested test plan

- [ ] PSE payin with `1000000001`: `pseUrl` appears when you poll, then `payin.confirmed`.
- [ ] Payin with `1000000003`: `payin.declined` with `errorCode: SANDBOX_DECLINED`.
- [ ] Payin with `1000000005`: `payin.canceled`.
- [ ] Bre-B `QR_CODE` payin: `qrString` appears when you poll.
- [ ] Nequi payin with `1000000001`: `sourceData.phone` matches the request, then `payin.confirmed`.
- [ ] Bre-B payout with `1000000001`: validate the key with `GET /breb/keys/{keyString}`, then `payout.confirmed`.
- [ ] Payment link: complete one and receive `paymentlink.completed`; let another expire and receive `paymentlink.expired`.
- [ ] Your webhook endpoint rejects requests without your authentication header.

## Sequence diagram

```mermaid
sequenceDiagram
    autonumber
    participant Client as Your server
    participant API as HelloPay sandbox
    participant WH as Your webhook endpoint

    Client->>API: POST /payins or POST /payouts (inlineCustomer.idNumber)
    API-->>Client: 201 Created, status PENDING
    Note over API: Prepares rail data (pseUrl, keyString, qrString)
    API-->>WH: payin.processing (payins only)

    loop Until sourceData is ready
        Client->>API: GET /payins/{id}
        API-->>Client: status PROCESSING, sourceData
    end

    Note over API: About 5 seconds later
    alt idNumber = 1000000003
        API-->>WH: *.declined
    else idNumber = 1000000005
        API-->>WH: *.canceled
    else 1000000001 or any other value
        API-->>WH: *.confirmed
    end
```
